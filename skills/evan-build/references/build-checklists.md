# Evan Build 接力模板、审查细则、收口清单与反馈修复

在更新阶段交接快照、执行 Open Code Review、触发跨线程接力、做最终阶段 PR 收口或处理 PR 评审反馈时按需读取本文件。

## 一、5 行阶段交接快照模板（回写至仓库外 `PLAN.md`）

每阶段完成 `git commit` 后，在 `PLAN.md` 的“阶段交接记录”下追加本阶段快照：

```markdown
### 阶段 <N> 交接快照（<已完成 | 阻塞>）
- 锚点与提交: 分支 `<branch>` | worktree `<abs-path-or-root>` | HEAD `<short-sha>`（本阶段提交）
- 改动偏差: <与计划强相关文件清单完全一致 | 补改了 `path:symbol`，原因：...>
- 关键裁决: <无 | 裁决：<决定> — <原因> — <影响>>
- 验证与审查: <已通过命令与退出码 0、OCR 结论>；未验证项：<无或具体原因>
- 交接给下一阶段（≤3 条）: <新定内部契约 / 已复用符号 / 需避开的坑，无则写无>
```

## 二、Open Code Review 判定细则

1. **工具选择** 优先加载 `open-code-review` skill 调用本机 `ocr` CLI（不是 MCP 工具，也不在仓库 npm script 中）；仅在 skill 无法加载或外部 OCR 模型不可连时降级 `open-code-review-delegate`。
2. **问题分级处理**
   - `critical` / `high` / 明确影响行为的 `medium`：统一汇总、集中修复、重跑受影响测试。
   - 低优先级 / 误报 / 超出本阶段范围：在交接快照中记录判断依据，不为单个问题额外重开审查。
3. **复审边界（单阶段硬上限 2 次）**
   - 默认每阶段仅做 1 次 OCR，常规修复经最新测试通过即可进入提交。
   - 仅当修复改动触及**核心对外接口、安全权限、并发正确性、或持久化/数据一致性**时，才对本阶段完整差异触发最多 1 次复审。
   - 复审发现的明确阻塞项集中修复并重测后直接进入提交，不再启动第 3 次审查；非阻塞项记为剩余风险。
4. **失败停点** 审查工具不可用、必要验收未通过或存在阻塞问题时，将 `PLAN.md` 本阶段状态置为 `阻塞`，写明原因与恢复步骤后停下，保留当前实际进度；若属于需要修订计划的真实阻塞，同时按 SKILL 第 2 节第 2 点把计划置为 `REVISING`。

## 三、跨线程接力协议（需授权的 T3 高优先级 + 降级）

### 触发前提
- 阶段之间：本阶段已提交，5 行交接快照已落盘。规划后首次切线程：无需虚构提交或快照，用冻结基线和已就绪的实施目录起步，且用户授权须包含首切。
- 当前无任何阻塞状态。
- **`PLAN.md` 中 `接力授权: 已确认`**。未授权或为 `不适用` 时一律不自动开线程，只输出下方降级提示词。

### 1. T3 Code 自动接力（最高优先级，需 `接力授权: 已确认`）
1. 调用 `t3_worktree_status` 核对 T3 项目根与 Git 实施目录；shell 切换目录不会改变旧线程绑定。跨项目时须指定目标项目，不靠继承；归属没有核实或绑定失败时退回手动接力，不回退到错误的 root。
2. 调用 `t3_thread_launch` 启动新顶层线程：
   - 在 worktree 中必须传 `workspaceStrategy: { type: "existing_worktree", worktreePath: "<abs-worktree-path>" }`。该参数已实测：用 shell 创建在 `~/.t3/worktrees/` 下的 worktree 可被正确绑定（线程工作目录与分支均一致），前提是该仓库已是 T3 项目。
   - 在原仓库根目录则传 `workspaceStrategy: { type: "root" }`。
3. 交接 `message` 只放极简指针（不长篇复述历史）：
   - 加载 `$evan-build`
   - `PLAN.md` 绝对路径
   - 刚完成的提交短哈希（若有）与阶段交接快照已更新
   - 剩余待执行阶段范围与推进模式（默认连续跑完，或单阶段汇报模式）
   - 转达 `PLAN.md` 已记录用户的接力授权，可按计划为剩余阶段开启新顶层线程接力
   - 最多 3 条未落盘临时注意事项（如有）
4. 在当前线程附上新线程链接后立即结束。

### 2. 降级接力提示词模板（未授权，或 Claude Code、Pi、终端 CLI 等无 `t3_thread_launch` 的环境）
触发换会话接力时，直接输出以下可复制块：

```text
$evan-build 继续执行计划
- PLAN.md: <abs-plan-path>
- 工作目录 / worktree: <abs-worktree-path>（分支 `<branch>`，当前 HEAD `<short-sha>`）
- 待执行阶段: 阶段 <next> 至 阶段 <end>（已更新阶段 <prev> 交接快照，先做双重真值核对后连续推进）
- 注意事项: <≤3 条，无则省略>
```

## 四、最终阶段 PR 交付摘要模板与收口清单

### 收口核对清单
- [ ] 全部阶段进度表均为 `已完成` 且已填入真实提交短哈希
- [ ] 已 `git fetch`，受影响范围的类型检查与 Lint 已基于最新提交跑通
- [ ] `git merge-tree` 对 fetch 后的最新参考分支只读预检无冲突（若有冲突仅汇报涉及文件与处理建议，由用户决定）
- [ ] 已对照参考分支完成 1 次整分支 Open Code Review（`--from <base> --analysis`）；轻量档仅在阶段审查覆盖完整待交付差异时省略
- [ ] 已向用户提议 `ci-test` 并按用户决定执行或跳过，结果如实记录
- [ ] 确认本地 `PLAN.md` 未进入任何 commit 与暂存区
- [ ] 已向用户说明将按计划 `同步方式`、`合并方式` 收口，并等待用户确认

### 可直接粘贴的 PR 交付摘要模板

```markdown
## 背景与目标
<1~2 句话说明解决的问题或新增的能力>；关联工单：<编号或无>

## 根因与关键设计取舍
- <修复类写本质根因与治本方案；新增/优化类写核心设计与二三阶影响应对>
- <关键复用与最小改动说明>

## 影响范围与兼容保护
- 涉及模块与核心文件: <列出强相关模块与主要文件>
- 跨模块契约与存量兼容: <说明对同事模块接口、老数据、缓存与默认配置的影响及保护>

## 验证结果
- 自动化检查: <实际执行的测试、类型检查、Lint 命令与结果；是否运行 ci-test 及结果>
- 人工验收与审查: <人工验收结论、整分支 Open Code Review 结论、`git merge-tree` 冲突预检结果>

## 剩余风险与待人工确认项
- <无，或逐条列出具体风险与建议关注点>
```

### 最终分支收口动作（等用户确认后执行）
- **同步** 按计划 `同步方式` 同步最新参考分支；`rebase` 后执行第五节的哈希映射与整体回归。
- **本地合回功能分支** 确认目标工作区干净，再按计划使用 `--ff-only`、`--no-ff` 或 `--squash`（后者还需提交并记下合回 SHA）。快进失败不擅自改策略。核实结果后先移除本次干净 worktree，再安全删除本次临时分支；squash 后普通删除被拒绝则保留并说明，不自动强删。直接在当前分支开发时没有合回或清理动作。
- **主分支起点** `git push`、创建 PR、合并 PR、删除分支均由用户逐项单独授权后才执行；待 PR 合入后再清理分支与 worktree。

## 五、rebase 后的提交哈希映射与整体回归

同步前记下旧 HEAD、实际重放序列的起点和新目标 SHA。同步后核对进度表，不假定所有提交都改号或一一对应：

1. 用 `git range-diff <旧起点>..<旧HEAD> <新起点>..<新HEAD>` 比较两个提交范围。`!` 表示补丁有变化，须核查；跳过、合并或不能对应的提交保留旧证据，停下核实，不猜新哈希。
2. 用确认后的映射更新进度表，保留原始阶段快照；追加同步记录，下次恢复优先用其中的新 HEAD（merge 也记新锚点）：

```markdown
### 同步记录（<日期>）
- 同步方式: `<rebase | merge>` 到 `<目标ref @ SHA>`；同步后 HEAD `<new-head>`
- 哈希映射: 阶段 1 `<旧>` → `<新>`；阶段 2 `<旧>` → `<新>`
- 冲突处理: <无 | 涉及文件与用户决定>
- 整体回归: <各阶段验证命令与退出码>
```

3. 把全部阶段的验证命令在最新代码上整体重跑一遍并核对输出，通过后才回到收口流程。`merge` 同步无需映射，但同样要整体重跑回归。
4. 若分支此前已被用户推送，rebase 后的强推由用户单独决定。

## 六、PR 反馈修复清单

用户说“修 PR 评审意见”或“修 CI 失败”时使用：

1. **收集反馈** 逐条整理评审意见或 CI 失败日志，区分“必须修改”“可选建议”“超出范围”，并列出改动点与对应文件。
2. **范围判断** 反馈涉及扩大功能范围、改变已定接口或数据契约时，按 SKILL 第 2 节第 2 点把计划置为 `REVISING`，停下交 `evan-plan`；否则继续。
3. **追加阶段** 在 `PLAN.md` 进度表追加 `阶段 N+k：评审修复`，状态 `实施中`，并在阶段说明里写明对应的评审意见或 CI 失败项。
4. **实施与验证** 按 SKILL 第 2 节做强相关 Diff 复核与硬验证；CI 失败的修复要复现并跑通对应命令。每次改码后基于最新代码重跑验证。
5. **审查边界** 像其他阶段一样审查本批完整差异，修后重测。默认不再重审整分支；核心接口、安全、并发或数据一致性的修复影响多个阶段时，才复核整分支。
6. **提交与回写** 按 `提交规范` 做本地提交（可在信息中说明对应评审意见），回写短哈希与 5 行交接快照，阶段置为 `已完成`。
7. **汇报并交还决策** 汇报修复内容、验证结果与未采纳的意见及理由，**由用户决定**是否 `push`、是否回复评审。
