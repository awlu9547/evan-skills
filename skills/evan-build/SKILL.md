# Evan Build

以仓库外 `PLAN.md`（默认 `~/.t3/plans/<repo>/<feature-slug>/PLAN.md`）中当前阶段的交付物、跨模块契约与验收标准为准。`PLAN.md` 本地留存且**绝不 commit、绝不 push**。

**默认连续推进策略** 只要 `PLAN.md` 已 `FROZEN`，默认按顺序一次性连续跑完全部阶段，每阶段独立验收、审查、提交并回写交接快照，遇真实阻塞立即停下。仅当用户明确要求“每阶段跑完跟我汇报”或仅授权指定阶段时，才在单阶段完成后停下汇报并预告下一阶段等待确认。

执行审查、接力或收口前，按需读取 [references/build-checklists.md](references/build-checklists.md) 中的模板与判定细则。

## 1. 找准计划、落地 worktree 与双重真值校验

1. **核对冻结状态与基准** 读取 `PLAN.md` 的 `状态`、`任务类型`、`执行方式`、分支与 worktree 策略、参考分支基准、进度表与最新“阶段交接记录”。仅在 `状态: FROZEN` 且前置阶段为 `已完成` 时开工；缺计划、待第二版或未定稿时说明缺哪一步并交回 `evan-plan`。
2. **阶段 1 落地分支与 worktree** 若 `PLAN.md` 选定了“基于当前分支新建分支”且尚未建好对应工作目录，先检查原目录未提交修改——任务依赖原目录未提交改动时停下请用户确认带入方式，无关改动保持原位；随后直接在 `~/.t3/worktrees/<repo>/<task-slug>` 创建新分支和独立 worktree 并切入实施。若目标分支与 worktree 已存在则直接复用。
3. **双重真值校验（连续接力与断点续跑）** 先读 `PLAN.md` 进度表五态（`待开始 / 实施中 / 已验证待审查 / 已完成 / 阻塞`）及上一阶段的 5 行交接快照，再用 `git rev-parse --short HEAD` 与 `git status --short` 核对仓库真实状态是否与交接锚点一致。一致时直接从下一待执行阶段或中断状态起步，不重复扫描整个仓库；若发现仓库偏离记录，或参考分支的新提交改变了本阶段依赖的接口、兼容要求或验收条件，记录证据并交回 `evan-plan` 或请用户确认。
4. **规划线程首切（T3 优先）** 若当前线程刚跑完 `evan-plan` 且计划确认了 `每阶段提交后换新线程接力`，在 T3 环境中建好 worktree（若需新建）后，直接按第 3 节第 4 条的 T3 接力协议为首个待执行阶段开启干净新线程起步。

## 2. 单线程实施、强相关 Diff 与硬验证

1. **单线程精准实施** 全程单线程编码，不拆多子 agent 编写耦合业务代码。沿 `PLAN.md` 列明的入口、符号与复用清单落实最小改动；修 Bug 先复现并根治，新增或优化用可观察行为验证。动工时先将当前阶段进度表状态置为 `实施中`。
2. **先裁决记账，不瞎停工** 计划里的小疏漏或私有实现微调直接合理裁决，按 `裁决：<决定> — <原因> — <影响>` 写入本阶段交接快照，不中断流程。只有涉及扩大功能范围、改变验收条件、改变对外接口或数据结构、破坏性操作或方案走不通时，才将状态标为 `阻塞`，暂停并交回 `evan-plan` 或请求用户确认。
3. **强相关 Diff 复核** 编码完成后、进入审查和提交前，强制执行 `git diff --stat` 与 `git status --short` 对照 `PLAN.md` 的“强相关拟改文件清单”，剔除无关修改和顺手格式化；因真实依赖补改的同范围调用方或测试同步记录到 `PLAN.md`。
4. **硬验证铁律** 运行本阶段验收命令以及 `PLAN.md` 列明的跨模块契约回归检查，记录实际命令、结果与未验证项（已有失败单列）。每次修改代码（包括修复审查问题）后，必须基于最新代码重跑对应验证命令并核对实际输出与退出码，严禁复用改前结果。验收通过后将阶段状态更新为 `已验证待审查`；必要验收失败则留在当前阶段修复重测。

## 3. Open Code Review、纯业务提交与阶段接力

1. **单阶段 Open Code Review（上限 2 次）** 对本阶段完整工作区差异（含新增文件）执行 **1 次** Open Code Review（优先加载 `open-code-review` 走本机 `ocr` CLI，不可用时降级 `open-code-review-delegate`）。集中修复 critical、high 和明确影响行为的 medium 问题并重跑受影响测试，低优先级、误报或超范围项记录判断依据。常规修复测试通过即可提交；仅当修复触及核心接口、安全性、并发正确性或数据一致性等高风险改动时，才允许执行**最多 1 次复审**（判定细则见 [references/build-checklists.md](references/build-checklists.md)）。修复属于已授权范围，无需逐条再问；若修复会扩大范围或改动已定设计/契约，立刻暂停确认。
2. **纯业务简体中文提交** 检查工作区与暂存差异，**只提交本阶段业务代码与测试改动**（绝不将仓库外或任何 `PLAN.md` 纳入提交）。提交标题和正文默认使用简体中文并保留项目约定的 type 前缀（如 `fix(auth): 修复令牌过期重复刷新`）。
3. **回写真实短哈希与 5 行交接快照** 提交成功后，立即将仓库外 `PLAN.md` 的本阶段状态更新为 `已完成`，填入**实际提交短哈希**与测试审查结果，并按 [references/build-checklists.md](references/build-checklists.md) 写入本阶段的 5 行“阶段交接快照”（锚点哈希与 worktree 路径、改动偏差、关键裁决、已验证/未验证项、下阶段注意事项）。未落盘交接快照前不得进入下一阶段或开新线程。
4. **连续流转与 T3 优先跨线程接力** 若仍有剩余待执行阶段：
   - **单阶段汇报模式（仅用户显式要求时）** 汇报本阶段交付、裁决、验证与风险，并用通俗中文简述下一阶段的目标、拟改文件、核心做法与验收方法，停下等待用户确认。
   - **默认连续模式 + T3 最高优先级接力** 当 `PLAN.md` 确认了 `每阶段提交后换新线程接力`，或原定 `单线程` 但触发动态安全阀（本线程已发生上下文压缩、经历密集排错或触发阶段内第 2 次高风险 OCR 复审）时：
     - **T3 Code 环境（高优先级）** 确认交接快照已落盘且本阶段已 `git commit`，先调 `t3_worktree_status` 核对工作区，再调 `t3_thread_launch`（在 worktree 中传 `workspaceStrategy: { type: "existing_worktree", worktreePath }`，否则传 `type: "root"`）携带极简指针开新顶层线程自动续跑剩余阶段，本线程附新线程链接后结束。遇阻塞立刻停在当前线程，禁止链式开新线程。
     - **其他 harness 降级（Claude Code / Pi / 终端 CLI）** 无自动启线程工具时，未触发上下文安全阀则在当前会话连续跑下一阶段；若已触发安全阀或计划要求换线程，按 [references/build-checklists.md](references/build-checklists.md) 输出可直接复制的极简接力提示词交用户开启新会话。

## 4. 最终阶段 PR 收口与用户确认门

最后一个阶段提交并回写交接快照后，依次完成以下收口检查：

1. 跑通受影响范围的类型检查与 Lint（全量 CI 留给 `ci-test` 按需触发）。
2. 用 `git merge-tree` 对最新参考分支做只读合并冲突预检。
3. 对照参考分支执行 **1 次**整分支收口 Open Code Review（`--from <base> --analysis`），核查跨阶段集成、行为影响与跨模块兼容性；明确阻塞集中修复、重跑回归并提交，不再循环启动 OCR，非阻塞项记入剩余风险。
4. 按 [references/build-checklists.md](references/build-checklists.md) 输出**最终验收汇报与可直接粘贴提 PR 的交付摘要**，并停下等待用户一句确认再执行最终分支收口：
   - **功能分支起点** 获确认后本地合回原功能分支，核对合入成功后再删除**本次新建的临时分支与对应 worktree**。
   - **主分支起点** 推送远端、创建或合并 PR 与删除分支均遵循用户单独授权。
   - 仅当本次排查或审查确实暴露了隐蔽项目坑或纠正了错误假设时，在最终汇报末尾顺带提一句是否值得补进回归测试或项目 `AGENTS.md`（由用户决定，绝不自动修改）。
