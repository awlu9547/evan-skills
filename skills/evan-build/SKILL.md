# Evan Build

以 `PLAN.md` 里当前阶段的交付物和验收标准为准。用户授权一个阶段就执行一个阶段；已明确授权多个阶段时，每个阶段仍单独验收和提交。

## 1. 找准计划和 Git 起点

读取 `PLAN.md` 的状态、已确认的 `执行方式`、目标分支、阶段依赖、进度和相关风险。只有 `状态: FROZEN` 且前置阶段已验收才开始实现。缺计划、待第二版或待用户定稿时，说明缺哪一步，回到 `evan-plan`。恢复任务时用工作区、实际提交和验证记录核对进度，接着做未完成的步骤。

若 `PLAN.md` 已确认 `执行方式: 每阶段提交后换新线程接力`，且当前线程前序刚跑完完整的规划与双方案合并，可直接按第 3 节第 5 条的接力流程为首个待执行阶段开启干净新线程起步，避免把规划讨论噪音带入编码。

核对当前分支、worktree、未提交修改，以及参考分支和开发分支相对计划基准的变化。沿用项目的分支和 worktree 约定，保护用户已有改动。新提交若与本阶段无关即可继续；若改变了依赖的接口、兼容要求或验收条件，记录证据，交回 `evan-plan` 修订受影响部分，确认后恢复。

## 2. 实施并验证当前阶段

全程坚持**单线程实施**，不拆多子 Agent 编写耦合业务代码，避免传话失真与实现漂移。沿计划列明的入口和调用方定位改动，复用现有实现。修 Bug 先复现，新增或改变行为用可观察结果验证。若需补改同一范围内的调用方或测试，把实际路径和原因同步到计划。

**先裁决记账，不瞎停工**：计划里的小疏漏或私有实现微调不中断、不打回重规划，直接合理裁决并记录到 `PLAN.md` 进度或交付说明（格式：`裁决：<决定> — <原因> — <影响>`）。只有涉及扩大功能范围、改变验收条件、改变对外接口/数据结构、破坏性操作或方案走不通时，才暂停并交回 `evan-plan` 或请求用户确认。

运行本阶段验收和受影响原有功能的回归检查，记录实际命令、结果及未验证项。已有失败单列说明。**硬验证铁律**：每次修改代码（包括修完 OCR 发现的问题）后，必须基于最新代码重跑对应验证命令并核对实际输出与退出码，禁止复用改前结果或凭推断宣称通过。必要验收失败时留在当前阶段，修复并重测。

## 3. 审查、提交、更新进度

1. 测试通过后，对**本阶段完整差异**执行 **1 次** Open Code Review（工作区模式，包括新增文件）。加载 `open-code-review` skill，按它的步骤执行审查。它用的是本机 `ocr` CLI，不是 MCP 工具，也不在仓库的 npm script 里。只有 skill 加载不了或模型连不上时，才改用 `open-code-review-delegate`。将本次审查发现的 critical、high 和明确影响行为的 medium 问题统一汇总，集中判断和修复。低优先级、误报或超出本阶段范围的问题记录判断依据，不为单个问题单独启动审查。
2. 修复后运行受影响测试。**默认每阶段只做这一次 OCR**，常规修复经测试验证通过即可进入提交，不再重复启动阶段内复审。只有修复涉及核心接口、安全性、并发正确性或数据一致性等高风险改动时，才对本阶段完整差异执行**最多 1 次复审**（单阶段上限 2 次，禁止“审查—修复—审查”循环）。复审中发现的明确阻塞问题集中修复并重测，不得再次启动 OCR；非阻塞问题记录为剩余风险。审查工具不可用、必要验收未通过或仍有阻塞问题时，记录原因和恢复步骤，停在本阶段，保留实际进度。
3. 阶段授权已经包含实施、测试、修复和提交本阶段内容时，视为已授权修复本阶段审查发现的明确问题，无需为每条审查意见单独请求确认。只有修复会扩大阶段范围、改变已确认设计、改变接口或验收条件，才暂停并交回 `evan-plan` 或请求用户确认。
4. 通过后检查工作区与暂存差异，只提交本阶段内容。把测试、审查结果和阶段状态随同本阶段一起提交。进度表用唯一的提交标题作标识（如 `feat(search): 阶段 1 合并重复请求`），避免在提交里填写自身哈希。提交完成后在交付消息附实际短哈希。
5. **阶段收尾与抗上下文腐烂接力**：汇报本阶段交付物、关键裁决、验证结果和剩余风险。单阶段授权在这里结束；若还有剩余已授权阶段，按以下规则流转：
   - **换新线程接力**：当 `PLAN.md` 已确认 `每阶段提交后换新线程接力`（或用户明确授权自动换线程）时，确认关键裁决已写回 `PLAN.md` 且本阶段改动已 `git commit`（从规划线程首切阶段 1 时只需 `PLAN.md` 已落盘且无半成品业务修改；保留用户无关未跟踪文件），先调 `t3_worktree_status` 确认当前分支与工作区，再调 `t3_thread_launch`（在 worktree 中必须传 `workspaceStrategy: { type: "existing_worktree", worktreePath }`，否则传 `type: "root"`）启动新顶层线程，并在本线程附新线程链接后结束。交接 `message` 只放极简指针：加载 `$evan-build`、`PLAN.md` 路径、刚完成的提交短哈希（若有）、明确的剩余已授权阶段编号、**转达用户已授权按 `PLAN.md` 为剩余阶段开新顶层线程接力**、最多 3 条未落盘注意事项（不做长转述）。遇阻塞立刻停在当前线程，禁止链式开新线程。
   - **动态安全阀**：即便原定 `单线程`，若本线程已触发上下文压缩、本阶段经历了密集排错或触发了阶段内第 2 次高风险 OCR 复审，且仍有剩余阶段，在完成当前阶段提交后主动提醒用户可换新线程接力（若已授权自动换线程则直接按上述流程切换）。
6. **最终阶段收口**：多阶段计划的最后一个阶段提交后，跑通受影响范围的类型检查/Lint，用 `git merge-tree` 只读预检与最新参考分支无合并冲突，并对照参考分支执行 **1 次**整分支收口审查（`--from <base> --analysis`，按 `open-code-review` 的分支对比流程），检查跨阶段集成、行为影响与兼容性（全量 CI 留给 `ci-test` 按需触发）。收口审查发现的明确阻塞问题集中修复、补跑回归并提交，不再循环启动 OCR；非阻塞问题记入剩余风险。仅当本次排查或审查确实暴露了项目隐蔽坑或纠正了错误假设时，在最终汇报末尾顺带提一句是否值得补进回归测试或项目 `AGENTS.md`（由用户决定，绝不自动改文档）。依项目约定和已有授权执行本地合并，分别报告已完成的验证和实际合并状态。推送、合并 PR 和部署遵循用户的单独授权。
