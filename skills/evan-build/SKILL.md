# Evan Build

用户明确要求开工后，默认连续跑完获准的阶段；仅授权某阶段或要求逐段汇报时，到指定边界就停。`FROZEN` 仅表示方案定稿，不等于开工、开线程或发布授权。`PLAN.md` 在仓库外留存，绝不 commit 或 push。

**权限边界：** 可以 fetch 更新本地引用、查看差异、预检冲突。默认只做本地提交。`git push`（含反馈修复后的再推送）、强推、创建或更新 PR、回复评审、合并 PR、远端删分支都须用户就本次动作和目标明确授权；允许 push 不等于允许提 PR，之前的授权不自动延续。

## 1. 找计划，核对工作现场

1. **定位计划。** 按“用户指定路径 → 本工作区指针 → 默认路径”查找。指针路径用 `git rev-parse --path-format=absolute --git-path evan-plan-ref` 取得，内容是一行计划绝对路径。默认是 `~/.t3/plans/<owner__repo>/<slug>/PLAN.md`；无 `origin` 用原仓库目录名，不用 worktree 名。核对候选的仓库、任务、分支；路径不匹配或不能唯一确定时请用户指明，不猜测或覆盖。
2. **核对交接。** 读取 `状态`、`规模档位`、`任务类型`、`执行方式`、`接力授权`、`计划绝对路径`、`分支策略`、`worktree 绝对路径`、`收口与 PR 路径`、Git 基准与进度表。仅在 `FROZEN` 且前置阶段已完成时开工；缺计划、待第二版、未冻结或 `REVISING` 时交回 `evan-plan`。旧计划保留原路径和进度：缺新字段时默认标准档、无接力或远端授权，实际影响分支操作的缺项先确认。
3. **落地工作区。** 核对原分支、基线 SHA、受保护分支规则及已有改动；需要带入未提交修改时先问，无关修改留在原处。用计划指定的基线和路径新建分支及 worktree（默认 `~/.t3/worktrees/<owner__repo>/<slug>`）；已有目录核对仓库、分支和路径一致才复用。受保护分支没有符合仓库规则的用户明确例外，不直接提交。在实际实施工作区登记同一计划指针，不覆盖其他任务的指针。
4. **从真实状态恢复。** 对计划指定的远端 `git fetch <remote>`；纯本地目标用本地 ref/SHA，fetch 失败不得称远端最新。用 `git rev-parse --short HEAD` 和 `git status --short` 核对最新交接或同步记录，首阶段用冻结基线。参考分支前进时用 `git diff --stat <旧SHA> <新SHA>` 定位，再读实际差异：仅文件重叠不必停；若改变契约或验收，转修订。记下已检查的 SHA，恢复第一个依赖已满足的未完成阶段。锚点或在途改动来历不明时先核实，不覆盖、不重复提交。

## 2. 单线程实施与验证

1. 将阶段置为 `实施中`，沿计划列明的入口与可复用实现做最小改动。修 Bug 先复现，新增或优化用可观察行为验证；不拆多个 agent 同时改耦合代码。
2. 私有实现微调记为“裁决：决定 — 原因 — 影响”，继续做。若需改变范围、对外契约、验收条件或阶段方案（含轻量任务超出门槛），将阶段置 `阻塞`、计划置 `REVISING`，在修订记录留下证据和现场，停下交回 `evan-plan`。若只是工具或测试环境暂不可用，只标阶段 `阻塞`，不解冻计划。
3. 提交前用 `git status --short`、`git diff --stat`、`git diff --cached` 对照强相关文件清单，另看新增文件内容。只暂存本阶段的修改，不清除或带入他人的修改；在同范围内补改调用方、测试等需记录原因。
4. 执行本阶段验收和跨模块回归，记录实际命令、退出码、已有失败及未验证项。**每次改码，包括修审查问题后，都基于最新代码重跑相关检查**。必要验收失败则修复重测；通过后置 `已验证待审查`。

## 3. 审查、提交与阶段接力

1. 对本阶段完整差异（含新增文件）做 1 次 Open Code Review，优先 `open-code-review`，不可用时降级 `open-code-review-delegate`。集中处理 critical、high 和确实影响行为的 medium，其他项记录判断。修复后重测；只有修复触及核心接口、安全、并发或数据一致性时最多再审 1 次。详见[审查细则](references/build-checklists.md)。
2. 只提交本阶段交付所需的代码、测试和配套文件。遵循 `提交规范` 与 `关联工单`，显式规则优先于最近 20 条提交的惯例；没有约定才用简体中文加 type 前缀。取得实际提交短哈希后，在仓库外进度表置 `已完成`，写入测试与审查结果，并按清单追加 5 行交接快照。未回写不进入下一阶段。
3. 需要换线程（计划要求、上下文压缩、密集排错或第 2 次高风险复审）时，**只有用户明确授权了对应阶段且 `接力授权: 已确认`** 才在 T3 调用 `t3_worktree_status`、`t3_thread_launch`。规划线程首切还须授权包含首切、计划已冻结且实施目录就绪。无授权、无法确认绑定或非 T3 环境则给可复制提示词并停下，不自动创建线程。无换线程需要则继续当前会话；阶段汇报模式优先停下。见[接力协议](references/build-checklists.md)。

## 4. 最终验收与分支收口

1. 刷新并固定本次实际合入目标的 ref/SHA，跑项目适用的类型检查与 Lint。用 `git merge-tree --write-tree <目标SHA> HEAD` 预检；冲突或预检失败即停下，只报告文件、错误及按 `同步方式` 的处理建议，不自动解决或推送。
2. 对照目标做 1 次整分支 OCR（`--from <base> --analysis`）；只有**轻量档且阶段审查已覆盖全部待交付差异**才省略。修明确阻塞后重跑回归，本地提交、补记最终 HEAD 和结果，不循环开审。提议用 `ci-test` 跑项目本地 CI，用户同意才调用；未运行如实写明，不替代必需的远端检查。
3. 给出[可粘贴的 PR 摘要](references/build-checklists.md)，区分“已在本地验证”和“已发布”。如需要实际同步，用户确认后才按 `同步方式` 对本次合回目标执行；已有推送的历史改写另行确认。rebase 后用 `git range-diff` 核实提交映射，merge 后记录新锚点。同步后重跑全部阶段验证、更新摘要，再收口。
4. **直接在当前分支做**：没有临时分支可合回或清理。**从功能分支另开临时分支**：确认后按 `合并方式` 本地合回并核实，只清理本次新建的对象。**从主线另开功能分支**：是否推送、创建或合并 PR、合入后清理，逐项由用户决定。若发现值得补进回归测试或项目 `AGENTS.md` 的隐患，只提建议，不顺手修改。

## 5. PR 反馈修复

收到“修 PR 评审意见”或“修 CI 失败”的要求时，先核对 PR 的 head、阶段及反馈是否已处理。范围内的一批意见追加为 `阶段 N+k：评审修复`，在同一计划写清意见、验收和文件；沿用范围检查、验证、阶段审查、本地提交与快照。不默认重复整分支 OCR；高风险修复影响多个阶段时才复核整分支。超出范围则转 `REVISING`。汇报已修、未采纳的原因和验证结果，是否再 push 或回复评审仍由用户决定。详见[反馈修复清单](references/build-checklists.md)。
