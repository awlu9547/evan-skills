# 已冻结计划的修订协议

`状态: FROZEN` 的计划在实施中需要变更时使用本协议。目标是：改得有记录、已完成的成果不被悄悄推翻、`evan-build` 能无歧义地继续。

## 一、触发来源

- `evan-build` 把阶段置为 `阻塞`，同时把计划顶部 `状态` 置为 `REVISING`，并在“修订记录”写入待确认草稿（触发原因与证据）。
- 参考分支出现新提交，检查实际差异后确认它改变了计划的前提、契约或验收条件；仅同文件改动不是修订理由。
- 用户在实施中途变更需求或验收条件。
- PR 评审意见扩大了范围或要求改动已定契约。

## 二、修订步骤

1. **保全现场** 读取 `PLAN.md` 进度表、最新阶段交接快照和阻塞证据；若 `状态` 尚未是 `REVISING` 则先置为 `REVISING`。修订期间不触碰业务代码与已有提交。
2. **只对受影响范围重做调研** 按计划刷新参考基准，记下审阅过的旧、新 ref/SHA，核对其对已完成阶段与待做阶段的影响；仅针对受影响阶段重做真实链路、根因或二三阶影响分析，其余阶段原文保留。
3. **已完成阶段不改写** 已完成阶段的状态、提交短哈希与交接快照保持原样。需要推翻或调整已完成成果时，追加“补偿阶段”（如 `阶段 2-补偿：<名称>`），写明要调整的提交哈希、原因与影响；不得用 `reset`、`amend` 回改已提交历史，除非用户明确决定。
4. **修订受影响的未完成阶段** 更新步骤、拟改文件清单、契约清单与验证命令，并仅对受影响部分重做 `plan-template.md` 的门禁自检。若修订改变了架构方向或核心契约且此前未开方案 B，询问用户是否补做一次方案 B。
5. **记录修订** 在 `PLAN.md` 第 10 节新开 `rev N`，已有本次待确认草稿就补全同一行；`状态` 在用户确认前保持 `REVISING`。
6. **汇报并重新冻结** 向用户汇报：哪些阶段被改、新增了哪些补偿阶段、风险与依据；用户确认后补上确认依据，将参考基准更新到本次实际审阅的 SHA，并标回 `FROZEN`。已解除阻塞的阶段无在途改动则回 `待开始`，保留在途改动则记下现场并回 `实施中`；旧验证作废。明确下一个依赖已满足的阶段，按原执行授权继续，不扩大阶段或发布授权。

## 三、修订记录行格式

```markdown
| rev | 日期 | 触发原因与证据 | 受影响阶段 | 处理方式 | 用户确认依据 |
|---|---|---|---|---|---|
| 2 | 2026-11-27 | 阶段 2 实施时发现 `ReportAPI.fetch` 需新增字段，同事模块 `Dashboard` 也在调用（`Dashboard.swift:88`） | 阶段 2、3 | 阶段 2 步骤改为向后兼容的可选字段；阶段 3 增加 Dashboard 回归检查 | <用户确认原话或日期> |
```

## 四、补偿阶段示例

```markdown
### 阶段 2-补偿：撤回对 `ReportAPI.fetch` 的破坏性签名变更
- 前置依赖: 阶段 2（提交 `a1b2c3d`）
- 要调整的成果: `a1b2c3d` 中把 `fetch(range:)` 改为 `fetch(range:, mode:)` 的签名变更
- 做法: 以向后兼容的默认参数方式重做，用新提交修正，不改写 `a1b2c3d`
- 验证命令与预期结果: <同阶段 2，并加 Dashboard 回归检查>
- 单阶段回滚方式: `git revert <本补偿阶段提交>`
```

## 五、重新交给 build 前自检

- [ ] 已完成阶段的状态、哈希与交接快照与修订前完全一致
- [ ] 修订记录已写明原因、证据、受影响阶段与用户确认依据
- [ ] 受影响阶段的文件清单、契约清单与验证命令均已更新
- [ ] 进度表已包含全部新增阶段（含补偿阶段）且状态为 `待开始`
- [ ] 顶部 `状态` 已回到 `FROZEN`，`evan-build` 可从第一个未完成阶段继续
