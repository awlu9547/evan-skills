# 企业级 PLAN.md 模板与门禁核对清单

在撰写 `PLAN.md`（或双方案中的 `PLAN_A.md`）与定稿自检时使用本模板。按任务性质保留对应分析区块，确保字段完整且直接兼容 `evan-build`。**轻量档**（仅 1 个阶段、拟改文件不超过 3 个、不改跨模块契约）改用文末的“轻量档精简模板”。

## 二、轻量档精简模板

仅当“1 个阶段、拟改文件不超过 3 个、不改跨模块契约”时使用。保留顶部全部字段（`规模档位` 写 `轻量`、`执行方式` 写 `单线程`、`接力授权` 写 `不适用`），正文只保留下列区块，其余区块省略：

```markdown
## 1. Git 基准（精简）
- 原仓库路径、当前分支与 HEAD、参考基准（ref/SHA）、实际合回目标与同步偏差

## 2. 问题与根因 / 影响（精简）
- 需求三句话
- 修复写一句本质根因与证据；新增或优化写一句二三阶影响结论

## 3. 强相关拟改文件清单
| 文件路径 | 操作 | 绑定的需求点或根因 | 改动概要 |
|---|---|---|---|

## 5. 单阶段实施与验证
- 实施步骤 / 验证命令与预期 / 回滚方式

## 8. 进度表
| 阶段 | 状态 | 测试与审查结果 | 提交标识 |
|---|---|---|---|

## 9. 阶段交接记录
## 10. 修订记录
```

轻量档在实施中若发现范围超出（阶段超过 1 个、文件超过 3 个或碰到跨模块契约），按修订协议转为标准档。

## 三、定稿前企业级门禁清单

定稿交用户确认前逐条打勾核实，缺项直接补进 `PLAN.md`：

1. **根因或二三阶推演闭环**
   - 修复类是否找到了最本质根因并有代码/复现证据？
   - 新增/优化类是否写透了跨模块、App 体验、系统复杂度与长期维护成本的二三阶影响？
2. **复用与最小改动**
   - 是否先检查了项目内可复用代码？
   - 每个新增函数/层/依赖是否都有“现有做法为何行不通”的硬理由？
3. **文件强相关**
   - 拟改文件清单里是否存在顺手优化、无关格式化或超出本次需求的文件？若有立即移出至“延后观察项”。
4. **跨模块协作与安全边界**
   - 端到端输入→处理→成功/失败状态是否闭环？
   - 同事负责的上下游模块接口、存量数据、缓存、配置默认值是否全部向后兼容？
   - 每个阶段是否都能独立验收且安全回滚？
5. **PR 就绪与流程合规**
   - 若启用了方案 B，是否已将 `PLAN_A.md`、`PLAN_B.md` 及 `HANDOFF_SECOND_OPINION.md` 清理干净，仅保留正式 `PLAN.md`？
   - `PLAN.md` 是否存放在仓库外本地路径，确保后续 PR 零规划草稿污染？
   - 顶部全部字段与四列进度表、修订记录区是否完整，可直接衔接 `evan-build`？
6. **协作约定与授权**
   - 同步方式、合并方式、提交规范、关联工单是否已依据仓库约定填写并经用户确认？
   - 当前分支为受保护分支时，是否未选择“当前分支直接改动”（或已记录用户明确要求）？
   - 选择“每阶段提交后换新线程接力”时，是否已明确询问并记录 `接力授权`？
   - 计划中所有 `push`、创建或更新 PR 的动作，是否均写明由用户决定？
