# Evan Plan

规划阶段只读业务代码，只更新用户指定目录里的计划文档，默认目录为 `docs/<feature-slug>/`。继续已有任务时先读原 `PLAN.md`，保留用户批注、已完成阶段和实际验证记录。

## 1. 从问题出发，审查现状

- 用三句话对齐需求：谁遇到了什么问题，有什么证据？怎样观察到问题已经解决？哪些原有行为必须保留？把用户明确要求的做法与尚可选择的实现区分开。能从代码或测试查明的先查，只有会改变目标或验收方式的疑点才问用户。
- 记录仓库、工作目录、当前分支与 HEAD、参考分支与提交号。**参考分支默认是最终合并目标**。优先采用用户指定或已有任务明确记录的目标；现有信息不能判断时确认目标，不凭 `main`、`develop` 或当前分支的 upstream 猜测。
- 查看 `git status --short --branch`。用 `git merge-base <参考分支> HEAD` 找到共同起点，分别查看两边以来与需求有关的提交和差异，另查工作区、暂存区及相关未跟踪文件。明确哪些行为属于参考分支、哪些来自当前分支、哪些依赖未提交工作。遇到难以解释的兼容处理，再查对应的 `git log -p` 或 `git blame`。
- 沿真实入口追到结果和失败路径，记录调用方、接口或数据约定、相关配置、可复用实现、已有测试及缺口。用仓库相对路径和符号定位。把观察结果、推断和待验证事项分别写清。

## 2. 评估复杂度并在本地写方案 A

先按客观条件评估任务复杂度，**默认标准档**；只有**同时满足**以下条件才归为**轻量档**：单模块局部改动、不改公共接口/数据模型/持久化或并发安全逻辑、实现路径基本唯一、1～2 阶段可完成。

在 `PLAN.md` 顶部写 `状态: DRAFT`，并标明 `复杂度: 轻量|标准` 与 `执行方式: 单线程|每阶段提交后换新线程接力`（轻量档或 1～2 个常规阶段选 `单线程`；3+ 阶段或单阶段重改动选 `每阶段提交后换新线程接力`，随定稿一起由用户确认）。从成功条件倒推：现有功能是否已满足？复用或小改哪里就足够？提出新依赖、新接口或新层时，说明简单做法在哪条验收条件上行不通。

正文写明 Git 基准、现状、目标与范围、选定做法和理由。**按可独立验收的功能切片划分阶段，把纯脚手架、类型定义、配置和文档折进对应功能阶段，不单独拆阶段**。每阶段列出前置依赖、实施步骤、现有文件与拟新增路径、受影响的原有行为、风险、验证命令或人工操作及预期结果。命令取自项目脚本或 CI。进度表留出阶段、状态、测试与审查结果、提交标识四项。

自检整条操作从输入到输出是否走得通、失败时状态是否正确，并核对接口向后兼容、存量数据与缓存兼容、配置/开关默认安全及单阶段可回滚。把发现修进方案，把仍缺证据的风险写成具体检查。

## 3. 让另一个模型独立写方案 B（轻量档可跳过）

**轻量档**可跳过本节，直接将精简 `PLAN.md` 交用户确认（正文必须写明归为轻量的依据，用户可随时要求补跑方案 B）。**标准档**必须独立出方案 B。

默认在 T3 Code 里派一个本地子 agent 独立出稿，省掉人工复制粘贴。

- 方案 B **必须避开当前主模型家族**，候选高推理模型如 `gemini-4-carbon`、`gpt-6.2-astra`、`claude-opus-5-5`（推理档位取 `high`）。派发前调用 `orchestrator_capabilities`，优先选用 `magpie` 下可访问的模型路径与对应选项键，`dogapi` 仅作兜底。
- brief 只放四样：用户原话、可观察的成功条件、Git 基准（参考分支与提交）、必须保留的原有行为和边界。要求它自己读仓库，把方案写进同目录的 `PLAN_B.md`，内容包括最小可行做法、阶段划分、兼容影响、验收方法和待核实的假设。
- **不要**附 `PLAN.md` 正文、文件清单、阶段安排或任何倾向性评价。有这些它就只会顺着改，第二版就白做了。
- 明确禁止修改业务代码，只允许写 `PLAN_B.md`。它带工具，不写这一句会顺手改文件。
- 所有独立模型均不可用、额度耗尽或不在 T3 环境时，退回文件交接：写 `HANDOFF_SECOND_OPINION.md`，只放需求、约束和 3～5 段关键代码，标出路径、符号和所属提交，交给用户自己的外部模型，并说明降级原因。

两种情况都把状态改成 `AWAITING_OPINION`，然后停下。子 agent 返回后先看它有没有真的读代码、有没有变成复述 A；跑偏就换模型或退回文件交接，不拿低质量结果凑数。

## 4. 收回 B，核实分歧并定稿

轻量档获用户确认后直接进入定稿；标准档在 `PLAN_B.md` 生成，或用户贴回外部版本的 B 之后，将状态改为 `MERGING`。逐项对照目标、代码证据、改动量和回归风险，记录有意义的分歧、采纳或舍弃的内容及原因。可以选 A 的实现、B 的测试；两版都没解决的缺口要单独补上。无法用事实裁定的产品取舍交给用户。

每条“不采纳 B”都要带证据：具体文件与符号、现有测试结果，或与验收条件冲突的位置。写不出证据的否决一律作废，重新判断。

把结论写回同一份 `PLAN.md`，核对文件定位、阶段依赖、验收标准和 `执行方式`。用户确认后标记 `状态: FROZEN` 并记录确认依据。交付计划、关键取舍和剩余风险。后续明确要求执行阶段时使用 `evan-build`。
