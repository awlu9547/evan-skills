# Evan Plan

规划阶段全程只读业务仓库，不修改业务代码，也不提前切换分支或创建 worktree。计划文档默认存放在 Git 仓库外的 `~/.t3/plans/<repo>/<feature-slug>/`（用户显式指定目录时按指定路径），本地长期保留且绝不 commit、绝不 push，原仓库与所有 worktree 共用同一绝对路径。继续已有任务时先读取原 `PLAN.md`，保留用户批注、已完成阶段和实际验证记录。

## 1. 只读调研、任务定性与深度评估

在生成任何计划文件之前，先完成只读调研，把事实摸清再向用户提问。

1. **对齐需求与验收标准** 用三句话收敛目标，即谁遇到什么问题及证据、怎样观察到问题已解决、哪些原有行为与跨模块契约必须保留。区分用户硬性要求与可选实现；能从代码、测试或 Git 历史查明的直接查明，仅在疑点会改变目标、兼容范围或验收方式时询问用户。
2. **记录 Git 基准与同步偏差** 记录仓库路径、工作目录、当前分支与 `HEAD`、参考分支（默认最终合并目标）与提交号；无法从上下文判断参考分支时向用户确认，不盲猜 `main`、`develop` 或当前 upstream。运行 `git status --short --branch` 与 `git merge-base <参考分支> HEAD`，厘清参考分支、当前分支与未提交修改各自包含的行为，并识别当前分支相对参考分支的合并偏差。
3. **追踪真实链路与盘点可复用实现** 沿真实入口追到正常结果与失败路径，用仓库相对路径和符号定位调用方、接口与数据约定、配置开关、已有测试及缺口，同时盘点仓库内现有可复用的模块和公共方法。明确区分事实、推断与待验证事项。
4. **按任务性质执行深度分析**
   - **Bug 修复** 从第一性原理出发，剥离表面现象并追到最本质的根因，用代码或复现链路证明修复方案能够治本。
   - **功能新增或优化** 除直接效果外，必须推演二阶、三阶影响，逐项评估对其他模块耦合、用户 App 体验（性能、交互一致性、边界状态、存量数据）、系统复杂度和长期维护成本的潜在影响；必要时先核查同类经典问题与项目成熟实践。
   - **混合任务** 修复部分做第一性原理根因分析，新增部分做二阶与三阶影响推演，同时严控范围扩散。
5. **预检修改文件强相关性** 初步列出拟改文件并逐个验证是否与本次需求或根因强相关，剔除顺手重构与无关改动。

## 2. 生成计划前的一次性确认门

落盘任何计划文件前，先探测当前环境可访问的模型能力，再基于第 1 节调研结果给出简洁评估与建议，一次性请用户拍板两件事。

1. **先探测可访问模型** 在支持跨模型派发的环境（如 T3 Code）先调用 `orchestrator_capabilities` 获取当前实际可访问的模型列表，过滤出与当前主模型不同家族的高推理候选模型（不写死模型型号）；若当前 harness 不支持自动跨模型派发或无可用异构模型，记录具体原因。
2. **向用户一次询问两项决策**
   - **是否启用方案 B 及所用模型** 结合改动跨度、架构分歧风险和核心契约影响给出是否建议开启方案 B 的依据；展示当前实际可访问的异构高推理模型列表并标出推荐项，由用户决定不开方案 B 或指定由哪个模型生成 `PLAN_B.md`。若环境无法自动派发，说明原因并请用户在“直接单方案”与“生成 `HANDOFF_SECOND_OPINION.md` 交由外部模型”之间二选一。
   - **分支与 worktree 策略** 给出建议并请用户确认是在**当前分支直接改动**，还是**基于当前分支新建分支**（默认在 `~/.t3/worktrees/<repo>/<task-slug>` 建立独立 worktree，跨 harness 通用）。同时确认收口规则：
     - 起点为功能分支时，基于该分支新建临时分支与 worktree，验收通过后合回当前功能分支并删除**本次新建的临时分支**。
     - 起点为主分支（如 `main`、`develop`）时，基于主分支新建功能分支与 worktree，验收通过后直接用新建分支提 PR 回主分支，待 PR 合入后再删除该分支。

未获得用户上述两项确认前，不得落盘 `PLAN.md`、`PLAN_A.md` 或 `PLAN_B.md`。

## 3. 生成方案（单方案或双方案并行合并）

撰写任何方案前，先读取 [references/plan-template.md](references/plan-template.md)，严格遵循其中的模板结构与企业级核对清单。

### 单方案路径（用户选择不开方案 B）

在计划目录直接生成 `PLAN.md`（初始 `状态: DRAFT`），进入第 4 节自检并交用户确认定稿。

### 双方案路径（用户确认开启方案 B）

1. **并行独立出稿** 立即使用用户指定的模型派发独立子 agent 读取业务仓库并将第二版方案写入同目录的 `PLAN_B.md`，同时主模型并行撰写同目录的 `PLAN_A.md`。
2. **严格隔离 brief** 给方案 B 的 brief 只包含五项信息，即用户原话、可观察的成功条件、Git 基准（仓库与参考分支/提交）、任务性质（修复需第一性原理根因分析 / 新增需二三阶影响推演）以及必须保留的原有行为与边界。严禁传入 `PLAN_A.md` 正文、文件清单、阶段安排或任何倾向性结论，并明确禁止修改任何业务代码，只允许写入 `PLAN_B.md`。
3. **无跨模型能力时的交接降级** 若用户选择了生成交接文件，在计划目录写入 `HANDOFF_SECOND_OPINION.md`（仅放需求、约束和 3～5 段标明路径、符号与提交号的关键代码），将 `PLAN_A.md` 标为 `状态: AWAITING_OPINION` 后停下，等待用户贴回外部模型的方案 B。
4. **质量检验与证据合并** 收到 `PLAN_B.md` 或外部方案 B 后先核对它是否真正基于仓库代码完成分析；若严重脱离代码或流于空泛，提示用户换模型重跑或改走单方案。确认有效后进入 `MERGING` 阶段，逐项比对目标达成、代码证据、复用程度、改动半径、跨模块兼容和长期维护风险。
   - 每条不采纳方案 B 的决定都必须附具体证据（文件路径与符号、现有测试或验收条件冲突）；写不出证据的否决一律作废并重新评估。
   - 可以组合 A 与 B 的最优部分，并补齐两版共同遗漏的缺口。
   - 遇到无法仅靠代码事实裁定的产品取舍或架构权衡，先列出选项、影响与推荐意见请用户拍板。
5. **汇总定稿并清理草稿** 将最终决策与完整方案写入同一份 `PLAN.md`，核对内容无误后**删除 `PLAN_A.md`、`PLAN_B.md`（及可能存在的 `HANDOFF_SECOND_OPINION.md`）**，计划目录最终只保留正式 `PLAN.md`。

## 4. 企业级门禁自检、定稿与 `evan-build` 衔接

在将 `PLAN.md` 交给用户确认定稿前，对照 [references/plan-template.md](references/plan-template.md) 逐项完成门禁自检并把发现直接修进方案：

1. **复用优先与最小改动** 已优先复用仓库现有实现；凡新增函数、抽象层、配置或依赖，均写清为何现有代码无法直接复用或微调；改动半径最小，不拖重原有调用链路。
2. **拟改文件强相关** 清单中每个文件都写明与本次需求或根因的直接对应关系；排查中发现的无关历史问题只记入“延后观察项”，与本次执行范围严格隔离。
3. **协作防改坏与长期可维护** 明确列出涉及其他同事模块的契约清单（接口签名、数据模型、事件、共享状态）与回归验证点；自检端到端正常路径、失败状态、存量数据与缓存兼容、配置开关默认安全、阶段按可独立验收的功能切片划分（脚手架、类型、配置与文档折入对应功能阶段）及单阶段可回滚。
4. **PR 就绪与 `evan-build` 兼容** 完整保留顶部 `状态`、`执行方式`（1～2 个常规阶段选 `单线程`，3+ 阶段或单阶段重改动选 `每阶段提交后换新线程接力`）、Git 基准、分支与 worktree 收口策略、PR 合入前同步与冲突预检要求、以及含四列（阶段、状态、测试与审查结果、提交标识）的进度表，并在顶部注明计划文件本地保留、不提交不推送。

交付 `PLAN.md` 路径、关键取舍和剩余风险给用户确认。用户确认后更新为 `状态: FROZEN` 并记录确认依据。后续用户明确要求执行阶段时，使用 `evan-build` 按冻结计划推进实施。
