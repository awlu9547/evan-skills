# `evan-plan` 技能

[English](README_EN.md)

`evan-plan` 用于为现有 Git 项目的 Bug 修复、功能新增或优化制定企业级分阶段开发计划，强调先只读调研代码与 Git 基准、通过前置确认门由用户决定是否开启方案 B 与新建 worktree 分支、收敛强相关最小改动范围，并在合并定稿后清理草稿、冻结为仓库外长期留存的 `PLAN.md`。

## 适合用它做什么

- 需求尚未完全对齐时，先从代码入口、调用方、测试缺口与 Git 历史查明现状。
- 对 Bug 修复做第一性原理根因分析，对新增或优化做二阶、三阶影响推演（含跨模块契约、App 体验、系统复杂度与长期维护成本）。
- 盘点可复用实现、证明新增抽象必要性，并校验拟改文件与需求/根因的强相关性。
- 按用户确认的模型并行独立生成 `PLAN_A.md` 与 `PLAN_B.md`，比对证据合并定稿为 `PLAN.md` 后删除草稿。

## 工作方式

1. **只读调研与深度分析**：对齐需求三句话、Git 基准及同步偏差、可复用模块，执行第一性原理根因分析或二三阶影响推演。
2. **前置一次性确认门**：先 `git fetch` 并探测项目协作约定（提交规范、同步/合并方式、受保护分支），再一次请用户拍板三件事：是否开方案 B（及用哪个模型）；分支与 worktree 策略（受保护分支不提供“当前分支直接改”，默认在 `~/.t3/worktrees/<owner__repo>/<slug>` 新建独立分支），连同同步方式、合并方式与提交规范；执行方式以及是否授权 `evan-build` 自动开新线程接力。
3. **生成与合并**：单方案直接写 `PLAN.md`；双方案则严格隔离 brief 并行产出 `PLAN_A.md` 与 `PLAN_B.md`，证据不足的否决一律作废，不确定取舍交用户拍板，汇总成正式 `PLAN.md` 后删除 `PLAN_A.md`、`PLAN_B.md`。
4. **企业级门禁自检与定稿**：按 `references/plan-template.md` 校验最小改动、强相关文件、跨模块契约与 PR 就绪度，用户确认后标记 `状态: FROZEN`。
5. **修订已冻结计划**：`evan-build` 阻塞或需求中途变化时，按 [修订协议](references/revision-protocol.md) 进入 `REVISING`：已完成阶段不改写（推翻只追加补偿阶段）、只重做受影响阶段、在“修订记录”写明原因与影响，用户确认后重新冻结。

## 典型请求

- “先用 `evan-plan` 调研下这个重构，出个分阶段方案。”
- “用 `evan-plan` 看看这个 Bug 的本质根因，再决定要不要跑双方案。”
- “继续完善 `~/.t3/plans/my-repo/auth-refactor/PLAN.md`，我把外部模型的方案 B 贴回来了。”

## 你需要提供

- 要解决的问题、目标功能或 Bug 现象。
- 目标合并分支（若当前上下文无法唯一判断，需明确指出参考分支）。
- 必须保留的原有行为、兼容性要求或特定约束。

## 产出

- `~/.t3/plans/<owner__repo>/<slug>/PLAN.md`：仓库外本地长期留存的正式计划（绝不 commit、绝不 push），包含状态机（`DRAFT` → `AWAITING_OPINION` → `MERGING` → `FROZEN`，冻结后可进入 `REVISING` 修订）、Git 基准、深度分析、强相关文件清单、契约回归、PR 就绪清单、五态进度表、阶段交接记录区与修订记录。
- `PLAN_A.md`、`PLAN_B.md`（及降级交接 `HANDOFF_SECOND_OPINION.md`）：仅在双方案生成与合并期间存在，定稿为 `PLAN.md` 后即刻删除。

## 边界

- 规划阶段严格**只读业务仓库**，不改业务源码，也不提前切分支或建 worktree。
- 若环境不支持跨模型自动派发，会说明原因并请用户在“转单方案”与“生成 `HANDOFF_SECOND_OPINION.md`”之间二选一。
- 只有标记为 `状态: FROZEN` 的计划才可交由下游实施。
- 规划与修订阶段不改工作区或索引；可以 fetch 更新本地引用，冻结时将计划绝对路径写入当前工作区的 Git 内部指针 `evan-plan-ref`，不 `push`、不创建 PR；这两类动作始终由用户决定。
- 小任务（仅 1 个阶段、不超过 3 个文件、不改跨模块契约）走轻量档：精简计划模板、只问分支策略。

## 相关技能
